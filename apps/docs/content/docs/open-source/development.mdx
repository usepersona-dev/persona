Persona is one repository with one pnpm workspace: `apps/web`, the app and its agent; `apps/landing`, the landing and the legal pages; `apps/docs`, this site; and `apps/files`, the files Worker. The paths on this page start from the repository's root.

## What you need

- **Node 24** and **pnpm**. `apps/web/` pins Node `24.x` in `engines`.
- **Postgres 15 or later.**
- **Redis 6 or later,** for the chat channels' state.
- **Docker.** eve runs each session's sandbox in a container locally; without Docker it falls back to a plain shell, and the sandbox setup (`apt-get`, `pnpm`) fails.
- **A [Clerk](https://clerk.com) application** with organizations on.
- **Model access** through the Vercel AI Gateway: a `VERCEL_OIDC_TOKEN` from `eve link`, or an `AI_GATEWAY_API_KEY`.
- **Accounts the code requires before a first chat:** [Autumn](https://useautumn.com) (credits: every turn checks them), Supermemory (loaded with the agent), Composio (the agent builds with it), and a bucket on any storage that speaks S3: Cloudflare R2, AWS S3 or MinIO (files).
- **[Browser Use](https://browser-use.com)** for the browser tools. A first chat runs without it; a browser task fails until it is set.
- **A domain for published files,** apart from the app's own domain. Pages that a persona writes run there, on another site than the app, so they can never act with a person's sign-in. One domain serves every persona: each gets a host of its own under it. See [The files Worker](#the-files-worker).
- **Accounts for the channels you want:** a Meta app for WhatsApp, a Telegram bot. Kapso is a legacy WhatsApp provider that our own older chats still use: leave its variables empty.

## Run it

```bash
pnpm install                 # once, anywhere in the repository: every app's packages
cd apps/web
cp .env.example .env.local   # fill it in, see Environment
pnpm db:migrate              # the tables
pnpm autumn:push             # the plans in Autumn
pnpm dev                     # the app and the agent on http://localhost:3000
```

Both are safe to run again at any time: the migrations run only what is new, and `autumn:push` sends only what changed in `autumn.config.ts`. Every build runs both too.

`pnpm dev` runs `next dev`. `withEve()` in `next.config.ts` starts the eve agent beside it and sends `/eve/v1/*` to it.

The landing and the legal pages are their own app in `apps/landing/`: `pnpm dev` there, on http://localhost:3001. `pnpm dev` at the repository's root starts the app, the landing and this site at once. Its variables are `NEXT_PUBLIC_APP_URL`, the app's origin, for the Sign in link, and the two PostHog variables below.

## Environment

All local variables live in `apps/web/.env.local`. Prisma reads it too. Keep every key on the Vercel project as well: `vercel env pull` and `eve link` replace the whole file with the project's development variables.

| Variable | What it is for |
| --- | --- |
| `DATABASE_URL` | Postgres, the direct address. Migrations always use it. |
| `DATABASE_POOLED_URL` | A PgBouncer in front of the database, production only. The app uses it when set. |
| `REDIS_URL` | Redis, for the chat channels' state (the Chat SDK). Its keys start with `chat:`. |
| `NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY`, `CLERK_SECRET_KEY` | Clerk. |
| `NEXT_PUBLIC_CLERK_SIGN_IN_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_URL` | `/sign-in` and `/sign-up`. |
| `NEXT_PUBLIC_CLERK_SIGN_IN_FALLBACK_REDIRECT_URL`, `NEXT_PUBLIC_CLERK_SIGN_UP_FALLBACK_REDIRECT_URL` | `/`. |
| `APP_URL` | The app's public origin. Vault links and webhooks are built from it. |
| `NEXT_PUBLIC_SITE_URL` | The landing's origin. The logo, the home page, Terms and Privacy links point at it. |
| `AGENT_TOKEN_SECRET` | Signs the agent tokens of the web channel. A secret you make. |
| `SECRETS_KEY` | Seals every value in the secrets table (AES-256-GCM): 32 random bytes in base64 (`node -e 'console.log(require("crypto").randomBytes(32).toString("base64"))'`). Required: without it the build fails. A lost key loses every value. Development and Preview share the dev database, so they take the same value; Production takes its own. |
| `AUTOMATIONS_SECRET` | The queue routes send it to the agent's own routes that start runs and post reports; those refuse any call without it. A secret you make. |
| `AUTUMN_SECRET_KEY` | [Autumn](https://useautumn.com): plans, credits and payments. `autumn.config.ts` holds the plans; `pnpm autumn:push` sends them to the account of the key. It matches each plan by its `planId`, so the file holds no ids of any account. The sandbox key (`am_sk_test_`) goes in `.env.local` and on Development and Preview; the live key (`am_sk_live_`) only on Production. |
| `VERCEL_OIDC_TOKEN` or `AI_GATEWAY_API_KEY` | Model access. The OIDC token also signs the calls to skills.sh: without it, Discover on the Skills page fails. |
| `S3_ENDPOINT`, `S3_REGION` | The storage, any that speaks S3: `https://<account id>.r2.cloudflarestorage.com` with `auto` on Cloudflare R2, `https://s3.<region>.amazonaws.com` on AWS S3, or a MinIO server's public address. Browsers, WhatsApp and the model provider open signed links to it, so it must answer on the internet over HTTPS. |
| `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY` | The storage's keys. |
| `S3_FILES_BUCKET` | The one private bucket that holds the files and the pictures. |
| `FILES_PREVIEW_URL` | Where the app shows a published file: `FILES_PREVIEW_URL/{personaId}/{fileId}` (a host of the app, like `https://files.usepersona.dev`). |
| `PUBLISHED_FILES_DOMAIN` | The domain of the files Worker, which serves a published file at `https://{personaId}.{domain}/{fileId}` and the pictures at `uploads.{domain}`. A domain of its own, not a name under the app's domain. See [The files Worker](#the-files-worker). |
| `SUPERMEMORY_API_KEY` | Memory. |
| `COMPOSIO_API_KEY`, `COMPOSIO_WEBHOOK_SECRET` | Apps, and the secret Composio signs each trigger event with. |
| `BROWSER_USE_API_KEY` | The browser. |
| `KAPSO_API_KEY`, `KAPSO_WEBHOOK_SECRET`, `KAPSO_PHONE_NUMBER_ID` | Legacy WhatsApp through Kapso, for chats that are already on it. Leave them empty: with no secret, the Kapso webhook refuses every call. |
| `META_APP_SECRET`, `META_ACCESS_TOKEN`, `META_WEBHOOK_VERIFY_TOKEN` | WhatsApp straight on Meta: the app's secret, a system user's token, and the token Meta sends when it verifies the webhook. |
| `META_PHONE_NUMBER_ID`, `META_PHONE_NUMBER` | The shared WhatsApp number on Meta, offered to every project. Leave them empty to offer none. |
| `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME`, `TELEGRAM_BOT_NAME` | The shared Telegram bot. |
| `TELEGRAM_WEBHOOK_SECRET` | Telegram sends it with every webhook, for every bot. |
| `NEXT_PUBLIC_POSTHOG_KEY`, `NEXT_PUBLIC_POSTHOG_HOST` | PostHog: the project's token and the host events go to. The landing and the docs take the same two. Leave the key empty to send nothing. See [Observability](/open-source/architecture#observability). |

## The database

The schema lives in `prisma/contract.prisma`, and its history in `migrations/app/`, as Prisma 8 migrations. A new database gets every migration:

```bash
pnpm db:migrate                # run the migrations the database has not seen
```

A schema change goes like this:

```bash
pnpm contract:emit             # write prisma/contract.json and contract.d.ts after a change
pnpm prisma db update          # make the development database match the contract, to try it out
pnpm prisma migration plan --name <slug>   # write the migration, chained from the last one
```

Read the plan before you apply it. A `DROP` loses data. The `build` script runs `pnpm db:migrate` before `next build`, so a migration ships with the code that uses it; a column drop goes in a later push than the code that stops using it, since the old deployment still reads it while the new one builds.

The Chat SDK keeps the state of the WhatsApp and Telegram chats in Redis: locks, duplicate checks, caches and recent messages, under keys that start with `chat:<channel>:`. To use the same Redis for something else, give it a prefix of its own. Keep Redis's eviction policy at `noeviction`, so Redis never drops a chat lock to free memory.

<Callout type="warn">
  Keep `@prisma/orm-postgres` on the same version as the `@prisma/orm-toolchain` that the `prisma` CLI pins. Check with `npm view prisma dependencies` before you upgrade either one.
</Callout>

## Tests

```bash
pnpm test                 # unit tests: they need no keys
pnpm test:integration     # the real database and services
```

The tests run on Vitest. Unit tests are in `tests/unit/` and get no keys. Integration tests are in `tests/integration/`, and `vitest.config.ts` gives them the keys from `.env.local`. The billing test needs an Autumn sandbox key (`am_sk_test_`) and talks to Autumn and Stripe's test mode. They call the agent's tools straight, against the real database. Each test makes its own organization, project and persona, and removes them at the end. The media tests call real models and the bucket, so they cost a few cents. The video test runs only with `TEST_VIDEO=1`. The live Telegram test runs only with `TEST_TELEGRAM_BOT_ID` and `TEST_TELEGRAM_CHAT_ID`, a test bot and a chat linked to a persona: it sends one message through the running dev server (`TEST_APP_URL`, `http://localhost:3000` by default) and checks that the chat got exactly one message for each `chat_say` and `chat_file` call.

## Evals

```bash
pnpm eval                      # every eval
pnpm eval vault                # one folder
```

`pnpm eval` is plain `eve eval`: eve loads `.env.local`, starts a local agent server and runs the evals one by one. Each eval makes a new persona with `t.context.makePersona()` and sends its token with every message. At the end, `evals/evals.config.ts` removes each persona and its browsers. The browser evals use Browser Use and take minutes. Keep the machine awake while they run.

## Deploy

Persona deploys to Vercel as three projects from the one repository, each with its app's folder as its Root Directory. A push to `main` deploys each project whose folder changed. The files Worker deploys to Cloudflare, see [The files Worker](#the-files-worker).

- `apps/web` (project `persona`) is the app on `app.usepersona.dev`. `withEve()` builds the agent into the same deployment and routes `/eve/v1/*` to it. The one schedule, `agent/schedules/start.ts`, becomes a Vercel Cron Job that runs every minute and puts due runs on Vercel Queues; `vercel.json` hands each queue to its route under `app/api/queues/`. `apps/web/package.json`'s `build` script is `pnpm db:migrate && pnpm autumn:push && next build`, so every build, on Vercel or any other host, migrates its database and pushes the plans before it builds; no build setting lives outside the repository.
- `apps/landing` (project `persona-landing`) is the landing and the legal pages on `usepersona.dev`.
- `apps/docs` (project `persona-docs`) is this site on `docs.usepersona.dev`.

Set every variable from [Environment](#environment) on Production, Preview and Development. On Vercel, the project's OIDC token gives model access, so no gateway key is needed. Set `APP_URL` to the app's origin and `NEXT_PUBLIC_SITE_URL` to the landing's, then point the shared WhatsApp number's and the shared bot's webhooks at the app: see [The shared number and bot](#the-shared-number-and-bot).

No Postgres or Redis yet? The Vercel Marketplace has both, Neon and Upstash. Put the database's direct address in `DATABASE_URL` (Neon calls it unpooled) and the Redis address in `REDIS_URL`. The other pages of these docs write the hosted app's address, `https://app.usepersona.dev`; on your own deployment, use your `APP_URL`.

The PostHog host on all three projects is PostHog's managed reverse proxy on a subdomain of yours: a `CNAME`, DNS only, to the target PostHog gives for the proxy.

No Vercel build touches Cloudflare. Cloudflare builds the files Worker itself from `apps/files`, see [The files Worker](#the-files-worker).

The app sits behind Cloudflare's proxy in production. With the proxy on, keep the domain's SSL/TLS mode on Full and leave "Always Use HTTPS" off: Vercel redirects to HTTPS itself, and it proves each name for its certificate with a plain HTTP call to `/.well-known/acme-challenge/`, so no setting or rule may redirect, challenge or block that path. The rate limit is one rule on the app's domain: 100 requests per 10 seconds per address on `/api/`, the persona webhooks and the collect page, with the rest of `/eve/v1/` outside it so channels and chats are never throttled. Add it by hand in Cloudflare, as a rate limiting rule on the app's zone. The security headers (`X-Frame-Options`, `X-Content-Type-Options`, `Referrer-Policy`) come from `next.config.ts`, with or without Cloudflare. Neither is required to run.

### The shared number and bot

The shared WhatsApp number and the shared Telegram bot come from the environment, so no screen sets their webhooks: set them by hand, once. A number or a bot has one webhook, so it reaches one environment at a time: point production's at production, and give a laptop or a preview a bot of its own. Leave them unset where you offer no shared number or bot. A number or a bot added in the app sets its own webhook.

The shared bot. `<bot id>` is the part of `TELEGRAM_BOT_TOKEN` before the colon:

```bash
curl -X POST "https://api.telegram.org/bot$TELEGRAM_BOT_TOKEN/setWebhook" \
  -H "Content-Type: application/json" \
  -d "{\"url\": \"$APP_URL/eve/v1/telegram/<bot id>\", \"secret_token\": \"$TELEGRAM_WEBHOOK_SECRET\", \"allowed_updates\": [\"message\"]}"
```

The shared number takes the three calls the app makes when it connects a number. `<app id>` is your Meta app's id, and `<account id>` the WhatsApp Business account that holds the number. Meta checks the address at once, so deploy the app with the `META_*` variables first:

```bash
# The app's webhook: the messages field, and the address Meta falls back to
curl -X POST "https://graph.facebook.com/v25.0/<app id>/subscriptions" \
  --data-urlencode "access_token=<app id>|$META_APP_SECRET" \
  -d object=whatsapp_business_account -d fields=messages -d include_values=true \
  --data-urlencode "callback_url=$APP_URL/eve/v1/meta/$META_PHONE_NUMBER_ID" \
  --data-urlencode "verify_token=$META_WEBHOOK_VERIFY_TOKEN"

# The account sends its messages to the app
curl -X POST "https://graph.facebook.com/v25.0/<account id>/subscribed_apps" \
  -H "Authorization: Bearer $META_ACCESS_TOKEN"

# The number's own address, which Meta uses before the account's and the app's
curl -X POST "https://graph.facebook.com/v25.0/$META_PHONE_NUMBER_ID" \
  -H "Authorization: Bearer $META_ACCESS_TOKEN" -H "Content-Type: application/json" \
  -d "{\"webhook_configuration\": {\"override_callback_uri\": \"$APP_URL/eve/v1/meta/$META_PHONE_NUMBER_ID\", \"verify_token\": \"$META_WEBHOOK_VERIFY_TOKEN\"}}"
```

### Channel webhooks

Each number and bot sends its messages to one address on the app:

| Channel | Webhook |
| --- | --- |
| WhatsApp on Meta | `{APP_URL}/eve/v1/meta/{phoneNumberId}` |
| WhatsApp on Kapso (legacy) | `{APP_URL}/eve/v1/whatsapp/{phoneNumberId}` |
| Telegram | `{APP_URL}/eve/v1/telegram/{botId}` |

Meta signs each request with the app's secret, Kapso with `KAPSO_WEBHOOK_SECRET`, and Telegram sends `TELEGRAM_WEBHOOK_SECRET` with each one. A number connected with `POST /api/projects/{projectId}/meta-lines` and a bot added in the app set their own webhooks. A number or a bot has one webhook, so it reaches one environment at a time. To test on your machine, point it at a public tunnel to `localhost:3000` and set `APP_URL` to the tunnel.

## The files Worker

Published files are served by the files Worker in front of the private bucket: `https://<personaId>.<PUBLISHED_FILES_DOMAIN>/<fileId>` serves the object `<personaId>/<fileId>` when its metadata says `public=true`, and anything under `uploads/` (the pictures) always. Its code is `apps/files/files.ts`. It reads the bucket through the S3 API with the app's own five `S3_*` settings, so any storage that speaks S3 works, and it runs in two places:

- **On Cloudflare**, as the Worker `persona-files` (`apps/files/wrangler.jsonc`). Cloudflare builds and deploys it from the repository: in the Worker's settings, connect the repository with Workers Builds, root directory `apps/files`, deploy command `npx wrangler deploy`, build watch path `apps/files/*`. Each push to `main` that changes the folder then deploys it.
- **With Node**, anywhere else: `pnpm start` in `apps/files` serves it on port 3001, with the five `S3_*` settings in its environment. A web server in front sends every `*.<PUBLISHED_FILES_DOMAIN>` request to it.

Set up once, by hand:

- the bucket's CORS rule: `GET`, `PUT` and `HEAD` from any origin, with a `content-type` header. Browsers upload straight to the bucket with a signed link, and read from it with one;
- on Cloudflare: the five `S3_*` settings as the Worker's secrets, the route `*.<domain>/*` on the zone of `PUBLISHED_FILES_DOMAIN`, and the proxied `AAAA` record `*` with the value `100::` that the route needs (a placeholder: the Worker answers);
- the rate limit on the app's domain, see [Deploy](#deploy).

`PUBLISHED_FILES_DOMAIN` is a domain of its own and not a name under the app's domain: the pages a persona writes run on it, and a page on the app's own domain could act with a person's sign-in. Each persona has a host of its own under it, so a page of one persona cannot reach another's.

The Worker is set up once per bucket, not per environment: every environment writes the same bucket, so a file published from your machine is live on the Worker's domain at once, and a local `.env.local` points `PUBLISHED_FILES_DOMAIN` and `FILES_PREVIEW_URL` at the same domain and file pages as production. Never set `FILES_PREVIEW_URL` to the app's own origin with no path: the proxy would take every request for a file page. The app's origin with a path, such as `http://localhost:3000/files`, works.

Without the Worker the app still runs, and files open inside the app through signed links. What has no answer is every public address: the link a persona sends for a published file, the "Open" button on a file page, and the pictures under `uploads/`. `FILES_PREVIEW_URL` must still be set, since `proxy.ts` reads it at startup: a second hostname that resolves to the app will do, and the proxy serves the file pages on it.

Leave the "Add security headers" switch of that zone off: its `X-Frame-Options: SAMEORIGIN` would stop the app's file pages from framing a file.
